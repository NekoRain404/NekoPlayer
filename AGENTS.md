# NekoPlayer

- Product direction: a PotPlayer-like desktop experience, C++20 / Qt 6 UI, libmpv as the playback engine.
- Every ordinary handwritten code file should stay at or below 500 lines, including tests and headers. The automated guard tolerates a small overage up to 550 lines; the explicitly listed coordination and desktop-integration files in `cmake/CheckCodeSize.cmake` may reach 800 lines; add an exception only with a written reason. Split by responsibility rather than by line count, and do not compress formatting to evade the limit.
- Keep playback state/commands, graphics resources, and desktop interaction in separate layers. Use explicit names and narrow interfaces; UI code must not issue raw mpv commands. Prefer shared QAction objects for PotPlayer-like menus, shortcuts and transport controls.
- The approved rendering approach is Qt Widgets + QOpenGLWidget + libmpv render API. Do not infer Qt Quick, a second playback engine, or a skin system as requirements.
- Use target-based CMake, explicit error handling, RAII, and Qt parent ownership where appropriate. Keep GUI work on the GUI thread.
- Review libmpv event delivery, callback lifetime, graphics-context requirements, and shutdown together when adding playback.
- `references/` contains ignored, independent shallow clones for study. Do not edit them as application source or add them as gitlinks. Verify licenses before reusing upstream code; NekoPlayer itself is GPL-3.0-only (see `LICENSE`).
- Build with `cmake --preset debug` and `cmake --build --preset debug`; run `ctest --preset debug` (locale is injected automatically). Use the sanitizer preset for lifetime-sensitive changes. Window tests run through the desktop presets; see `docs/development.md`. GUI offscreen startup is not proof of video rendering, hardware decoding, or HDR correctness.
- Layers: `playback/` state and libmpv commands (`mpv/`, `media/`, `playlist/`, `render/`), `session/` persistence, `input/` scanning/drop, `preview/` thumbnails, `library/` media index, `playlist/` M3U8, `ui/` Qt interaction (`window/`, `dialogs/`, `menus/`, `panels/`, `theme/`). Tests mirror the same layout under `tests/`. Keep UI free of raw mpv commands.
- Start with `docs/README.md` (documentation map), then `docs/development.md` (build, layout, conventions) and `docs/features.md` (observable behaviour). Update `docs/features.md` for user-visible behaviour, `docs/verification.md` for new test evidence, and keep the README as an overview with screenshots rather than a second feature manual. Relevant installed skills and source links are in `docs/skills.md`. Follow the user's scope; installing workflow skills does not itself authorize unrelated tasks.
